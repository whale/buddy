Overview

One system, three pressure levels

Buddy re-themes itself by active task count, entirely through CSS custom properties. Every surface reads from tokens so it adapts automatically. The cardinal rule: never hardcode an adaptive color — bind it to a token. This guide is the visual mirror of that system and flags where the code drifts from it.

lvl0 — normal
≤4 active · black on white
lvl1 — warning
5 active · text turns red
lvl2 — full
6 active · whole drawer red, text light

Keeping red vivid — OKLCH, not a black veil

A black overlay lowers lightness and drains chroma → the red goes muddy. Darkening in OKLCH (lower L, hold chroma + hue) keeps it a rich red. The same lower-L move still works on white automatically (white has no chroma to lose), so it's one mental model.

White-surface hover/selection keeps the lower-L move too (white → light grey), so the rule is uniform; only black-filled pills invert to lighten (raise L).

Adding punch — chroma boost & blend modes

Lower-L alone reads flat. These keep the red saturated. OKLCH can push chroma into the P3 gamut (your Mac display) — so judge these in Arc; the screenshots above are sRGB and undersell them. Hover the rows.

Recommendation: B — oklch(from var(--red) calc(l − .05) calc(c + .05) h) for the "now"/hover red. It darkens and gains chroma, so it punches without going neon. C (explicit P3) is punchier still if you want maximum vibrance; D (multiply ×saturated-red) is the blend-mode route — same family, less controllable. We can also nudge the resting red itself toward P3 if the whole lvl2 should feel more vivid.

Completed past tasks show the done word + strikethrough. Skipped (undone) tasks show plain, with a restore arrow (↩) to send them back to today.

Verified against dist/index.html. The system is largely consistent (adaptation via class hooks + lvl2 overrides). Below: what was just resolved, and the remaining consistency opportunities — none currently break legibility on red.
